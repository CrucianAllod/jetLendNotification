# JetLend Notification

Django-проект для импорта рассылок из XLSX-файла с последующей отправкой писем
через management command.

Каждая строка файла — одно письмо. Импорт сохраняет письма в базу, защищаясь от
повторной обработки по `external_id`, затем отправляет все письма, ожидающие
отправки. Отправка по условию задачи имитируется записью в лог с задержкой.

## Технологии

- Python 3.12+;
- Django 5.2;
- PostgreSQL 16;
- `uv` для зависимостей и виртуального окружения;
- Gunicorn для production-запуска;
- Ruff, mypy и django-stubs;
- Docker и Docker Compose.

## Локальный запуск

Необходимы установленные `uv`, Docker и Docker Compose.

```bash
cp .env.example .env
make install
make db-up
make migrate
make run-dev
```

Импорт тестового файла из `examples/notifications.xlsx`:

```bash
make import
```

Административная панель доступна на <http://127.0.0.1:8000/admin/>.
Создание администратора:

```bash
make superuser
```

PostgreSQL для разработки слушает порт `5434`, чтобы не конфликтовать с
другими локальными экземплярами.

## Импорт рассылок

### Формат файла

Первая строка — заголовки колонок. Колонки сопоставляются по имени без учёта
регистра, порядок и лишние колонки не важны. Читается первый лист книги.

| Колонка | Описание |
|---|---|
| `external_id` | Уникальный идентификатор записи во внешней системе |
| `user_id` | Идентификатор пользователя, целое число |
| `email` | Email получателя |
| `subject` | Тема письма, до 255 символов |
| `message` | Текст письма |

Все колонки обязательны. Полностью пустые строки пропускаются и в отчёт не
попадают.

### Команда импорта

```bash
uv run python manage.py import_notifications path/to/file.xlsx [--batch-size N] [--skip-send] [--dry-run]
```

| Опция | Назначение |
|---|---|
| `--batch-size N` | Сколько строк сохранять одним запросом. По умолчанию `NOTIFICATIONS_IMPORT_BATCH_SIZE` |
| `--skip-send` | Только импортировать, письма оставить в статусе «ожидает отправки» |
| `--dry-run` | Проверить файл и показать отчёт, ничего не сохраняя и не отправляя |

Пример вывода:

```text
Импорт завершён: examples/notifications.xlsx
  обработано строк:   24
  создано записей:    20
  пропущено записей:  1
  ошибочных строк:    3
Отправка завершена
  отправлено писем:   20
  ошибок отправки:    0
```

Счётчики связаны инвариантом `обработано = создано + пропущено + ошибочных`.

- **Пропущенные** — записи, чей `external_id` уже есть в базе или уже
  встречался выше в этом же файле. Повторный импорт того же файла ничего не
  создаёт и не отправляет повторно.
- **Ошибочные** — строки, не прошедшие валидацию: пустые обязательные поля,
  некорректный email, нецелочисленный `user_id`. Причина каждой ошибки с
  номером строки пишется в лог с уровнем `WARNING`, остальные строки файла
  импортируются.

Если файл не найден, не является XLSX или в заголовке нет обязательных колонок,
команда завершается с ошибкой и ненулевым кодом возврата.

### Отправка

После импорта команда отправляет **все** письма в статусе «ожидает отправки»,
а не только созданные в этом запуске. Так прерванный запуск можно продолжить,
просто повторив команду. Статус каждого письма сохраняется сразу после попытки
отправки, поэтому уже отправленные письма при повторе не уйдут второй раз.

Отправка имитируется записью в лог с задержкой `NOTIFICATIONS_SEND_DELAY`
секунд на письмо. Письма, оставшиеся в очереди после `--skip-send` или сбоя,
можно отправить отдельно:

```bash
uv run python manage.py send_notifications
# или
make send
```

### Тестовый файл

`examples/notifications.xlsx` содержит 20 корректных строк, дубликат и три
ошибочные строки. Файл любого размера можно сгенерировать скриптом:

```bash
make sample SAMPLE_ROWS=100000 FILE=examples/big.xlsx
make import FILE=examples/big.xlsx
```

### Как это устроено

Код приложения `notifications` разбит на слои:

- `services/xlsx_reader.py` — потоковое чтение файла через `openpyxl` в режиме
  `read_only`; файл не загружается в память целиком.
- `services/validation.py` — Django-форма для валидации строки.
- `services/importer.py` — импорт батчами: на каждый батч один `SELECT`
  существующих `external_id` и один `bulk_create`, число запросов не зависит
  от размера файла.
- `services/sender.py` — обход очереди и имитация отправки письма.
- `management/commands/` — команды `import_notifications` и
  `send_notifications`.

Письма хранятся в модели `Notification` со статусом `pending`, `sent` или
`failed` и доступны в административной панели.

## Docker

Dev-стек с autoreload и монтированием исходного кода:

```bash
make docker-dev
```

Production-like стек с Gunicorn:

```bash
cp .env.example .env
# Замените значения на реальные production-значения.
make docker-up
```

Сервис `app` ждёт готовности PostgreSQL, применяет миграции и запускает
Gunicorn. Production-конфигурация не содержит значений по умолчанию и требует
`DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS` и
параметры PostgreSQL из окружения.

## Логирование

Логи пишутся в stdout в формате `время уровень [logger] сообщение`. Уровень
задаётся переменной `DJANGO_LOG_LEVEL` (по умолчанию `INFO`), SQL-запросы
включаются отдельно через `DJANGO_DB_LOG_LEVEL=DEBUG`.

## Переменные окружения импорта

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `NOTIFICATIONS_IMPORT_BATCH_SIZE` | `1000` | Размер батча при сохранении строк |
| `NOTIFICATIONS_SEND_DELAY` | `0.1` | Задержка в секундах, имитирующая отправку одного письма |

## Проверки и тесты

```bash
make check
make test
```

`make check` запускает Django system check, Ruff lint, Ruff format check и
mypy. Тесты используют стандартный Django test runner и требуют запущенной
PostgreSQL (`make db-up`).
